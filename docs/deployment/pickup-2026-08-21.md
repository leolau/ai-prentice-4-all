## The incident every check we have said nothing about

On **2026-08-20 16:03 CST**, twelve units were stopped **and disabled**:
`hermes-gateway`, `hermes-digest`, `hermes-escalation`, the three
`hermes-email-*`, the four `hermes-wa-*`, and both `hermes-calendar-*`. The
gateway's own exit was orderly (`SIGTERM` → drain → `Exiting with code 1 …so
systemd Restart=on-failure can revive the gateway`), and systemd correctly did
**not** revive it, because an explicit `stop` is not a failure. `agent-home`,
`hermes-dashboard`, `hermes-embed` and the four timers were untouched, so the
phone app kept answering 200 and the public URL kept serving — the agent was
unreachable for **21 hours** while every surface a health probe touches looked
healthy. Restored on 2026-08-21 12:48 (`enable` + `start`, all twelve
`enabled/active`, running as `hermes`).

**Why nothing caught it, and this is the part to fix:** the captured state holds
unit *files* and drop-ins — their content — and `deploy_state.py check` compares
those, plus any unit installed on the box the snapshot has never seen. Nothing
in the record says *which units are supposed to be enabled and running*, so
twelve dead services are not drift by construction. `disabled` is worse than
`inactive`: a reboot would not have brought them back either. The fix shape is
small and in keeping with the rest: capture `is-enabled`/`is-active` per unit as
reviewed state, and have `check` report a captured-enabled unit that is disabled
or inactive as drift. Until that exists, **a box visit must ask
`systemctl is-enabled`/`is-active` per unit** and never infer liveness from a
`curl` against `:3100` or the public host.

Second finding from the same restore, still open: once running, the gateway
loops on

```
Conflict: terminated by other getUpdates request; make sure that only one bot instance is running
```

There is exactly **one** gateway process on the box (`ps` confirms), so a second
instance of the same Telegram bot token is polling from **off-box**. Two pollers
steal the long-poll from each other, so replies are erratic rather than absent —
the failure mode that looks like flakiness. Do not "fix" this by restarting
things; find the other holder of the token first. It is also the most plausible
reason someone deliberately stopped and disabled the twelve units on Aug 20.

## Know-how that is not obvious from the code

The durable set lives in
`../../.agents/skills/testing-hermes-systest-box/SKILL.md` (~30 traps, read it
before touching the box). The ones this arc added or re-learned:

- **Liveness is not reachability.** `agent-home` on `:3100` and the public
  `/login` both answer 200 with the gateway dead. Probe the unit, not the port.
- **`Agent Home needs a connection to reach your agent` is not an application
  error.** It is `agent-home/public/offline.html`, served by the service worker
  only when the browser's own navigation fetch never completed (`sw.js`:
  navigations are network-first, `/api/` and `/auth/` are not intercepted). It
  cannot distinguish a dead phone network from a dead origin, and the PWA keeps
  showing it until one navigation succeeds. Do not read it as evidence about
  the box.
- **Caddy keeps no request log.** `/etc/caddy/Caddyfile` is a hand-written
  two-line reverse proxy to `127.0.0.1:3100` with no `log` directive, and
  `/var/log/caddy` is empty — so "did the user's request ever reach the box?"
  is currently unanswerable, which is the one fact worth having during an
  outage report.
- **The layer-4 schema is `owner_user_id`, not `principal_id`**, and
  `principals` names its label column `display`. Guessing either produces an
  `UndefinedColumnError` that reads like a missing table.
- **Bare-Python datastore probes need the dotenv loaded first**
  (`from hermes_cli.env_loader import load_hermes_dotenv; load_hermes_dotenv()`),
  otherwise the DSN is empty and the failure looks like a connectivity problem.
- **The dashboard's session minting class is `plugins/dashboard_auth/basic`**,
  not `hermes_cli.web_server` — the import a cold agent tries first fails.
- **`hermes profile suggest` answering "no suggestion" is usually a gate, not a
  bug.** Generation needs: no open suggestion, the monthly clock elapsed
  (`_generation_due`), **two** skills with recorded uses, and one corroborating
  signal. On this box the skill bar is unmet, so the FG-30 adoption path cannot
  be exercised without fabricating production rows — which is not permitted.
- **Root-owned files in `HERMES_HOME` break `hermes` reads far from where they
  were created.** Two of them (`config.yaml.bak-1786027505`, `uploads/`) broke
  `--clone-all` weeks later. Anything a root command leaves behind is a future
  defect; `chown hermes` it in the same visit.
- **A shutdown that logs `Exiting with code 1 … so Restart=on-failure can revive
  the gateway` is not evidence that it was revived.** systemd does not restart
  after an explicit stop, and `Restart=on-failure` cannot help a disabled unit.

## Open, with the one thing that unblocks each

1. **The box is behind `develop`** — `763eb6e2d` vs `f605f8088`; the projects
   lane (#304–#314) has never been deployed. *Unblocks:* a deploy, and someone
   who owns that lane confirming it should go out.
2. **The duplicate Telegram poller** (above). *Unblocks:* knowing who else runs
   the token; nothing on the box can answer it.
3. **Enabled/active state is not captured**, so twelve dead units read as no
   drift. *Unblocks:* nothing — this is a small, self-contained PR to
   `deploy_state.py` and the manifest, and it is the highest-value ops fix open.
4. **FG-28 secret isolation cannot fail, so it cannot pass** — `default` and
   `maintenance` share one Supabase credential. *Unblocks:* a second distinct
   credential; only Leo can provide it.
5. **FG-30 D2 adoption and D3's success branch are untested.** *Unblocks:* real
   skill usage accumulating on the box, or an explicitly approved test-only
   generation path.
6. **The memory map's geometry is unverified** — the data is proven, the drawing
   is not, because the box has no browser. *Unblocks:* a browser session against
   the authenticated page.
7. **The gateway unit's drain contract is inconsistent** —
   `TimeoutStopSec=20s` with `drain_timeout=0s`, which the gateway itself warns
   about (`systemd may SIGKILL the gateway mid-drain`). *Unblocks:* deciding
   between `hermes gateway install --force` and shortening
   `agent.restart_drain_timeout`.
8. **`/etc/caddy/Caddyfile` is the public entry point to the agent and is in no
   repository and no captured state**, with no request log. *Unblocks:* a
   decision to bring it under the state repo (it is the last hand-written piece
   of this deployment).
9. **Digest delivery is not idempotent.** Database dedupe stops duplicate
   *rows*, not duplicate *pushes*: the UAT's second run re-delivered the W34
   digest to Telegram. *Unblocks:* a decision — dedupe on delivery, or accept it.
10. **Two stale root processes** on the box: a `hermes dashboard` (30 days) and
    a `next dev -p 4349` serving `tools/systest_notes` (39 days). Both violate
    the unprivileged-service model. *Unblocks:* confirming nobody depends on the
    notes tool before killing them.

## Rules that are not negotiable here

- **No SSH.** Everything goes through Alibaba OOS —
  `/home/ubuntu/run_on_box.sh <script-file>` in a session, or `aliyun ecs
  RunCommand` (region `cn-hongkong`, instance `i-j6c81aisv2dd8mg17yle`). OOS
  runs as **root** and under **`dash`**, not bash.
- **Run Hermes as the service user:**
  `sudo -u hermes -H env HERMES_HOME=/opt/data/hermes-home-staging …`. Root git
  commands need `-c safe.directory=/opt/data/hermes-agent`.
- **Do not fix application behaviour on the box.** A live edit is drift by
  definition: branch → PR → merge → deploy, then verify live.
- **Destructive live tests use throwaway principals and profiles the test
  created**, with teardown, and the visit ends with the box back at `default` +
  `maintenance`.
- **Never print a secret value**, including into a log the state repo captures.
